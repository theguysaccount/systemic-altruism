# Contributing evidence

Start with a public source and a precise, scoped claim. Use the issue template for corrections or a proposed organization. Please never submit private beneficiary information, credentials, or restricted source databases.

A data pull request should include:

1. Canonical organization identity and the assessed program or mechanism.
2. Primary source URL, title, retrieval date, and separate publication/evaluation date where known.
3. Original factual summary; do not copy protected evaluator prose.
4. A rationale and source for every changed axis; use `null` for unreviewed values.
5. Selection status: current recommendation, historical program review, or illustrative inclusion.
6. Evidence limitations, potential harms, the next falsifiable question and review confidence.
7. Disclosure of maintainer/evaluator/funder affiliations or conflicts.

Maintainers must check provenance, rights and scope before publication. A law is not enforcement; a pledge is not compliance; a funding gap is not proof of marginal outcomes. Do not extrapolate a trial or evaluator recommendation to every program of an organization.

Run `npm run build`, `npm test` and `npm run check`. New public routes need their own share card. Proposed changes to the method require a version change and an explanation of sensitivity to weights and missing evidence. Initial annotations still need independent human and affected-community review; please help improve that process.
